# MolaSearch 搜索基准测试方案（Bench Plan）

> 状态：**提案**（本目录所有文件都是提案，不是 as-built）。
> 日期：2026-10-24。
> 五个重点场景各映射到学界成熟基准；每个场景给出双层执行方式
> （离线回放 / 真实网络）、指标、判分脚本与 molasearch 的落点。
> 本文的对立面是 as-built 参考（`magpie/docs/subsystems/`），
> bench 落地一步，对应参考更新一步。

## 0. 总原则（继承 magpie 的验收哲学）

1. **双层执行**：`replay` 层离线确定性（真实抓包存成 fixture，httptest 回放，
   CI 可跑、永不触网——magpie 规则 "A test never reaches the network"）；
   `live` 层每夜真网跑一次并出报告。两层共用同一份 case 与同一套计分。
2. **真实输入**：fixture 来自真实厂商响应、真实 a11y 树、真实弹幕 XML，
   含缺字段、空值、畸形页（magpie：Tests use real inputs）。
3. **每个指标可复算**：报告 JSONL 里保存原始命中与判分中间值，
   任何人重跑脚本得到同一分数。
4. **回归门**：每次发版记录指标基线；4 类判定准确率下滑 >2% 或
   ABSTAIN 精度下滑 >5% 判失败（不修就红的 bench 版本）。
5. **bench 目录**（提案）：
   ```
   bench/
     fixtures/   # 抓包回放（按通道分目录）+ a11y 树 + 弹幕 XML + 视频帧
     cases/      # JSONL：{query, mode, gold, goldType, source}
     runners/    # 每场景 runner（Go test 或 python）
     reports/    # JSONL 明细 + markdown 摘要（按发版归档）
   ```
   CLI 入口提案：`molasearch bench modes|device|strategy|rag|video --suite replay|live`。

## 1. 场景一：设备操控搜索（M28 Computer-Use / M29 ADB）

**molasearch 的定位**：不是做 GUI agent，而是做"设备状态之上的搜索层"——
给定无障碍树 / ADB 组件树 / DOM 快照，找出答案并给引用。

**借用基准**：
- [AndroidWorld](https://github.com/google-research/android_world)（116 个程序化任务、20 个真实 App、模拟器 + 自动奖励信号）——真机层任务源
- [OSWorld / OSWorld-Verified](https://www.emergentmind.com/topics/osworld-verified-and-androidworld-benchmarks)——桌面侧对应物
- [MobileAgentBench](https://arxiv.org/html/2405.14573v3)、[MobileWorld (2025-12, 原生 MCP 支持)](https://www.alphaxiv.org/abs/2512.19432)——手机操控 + MCP 生态
- [ScreenSuite](https://huggingface.co/blog/screensuite)——统一评测 harness，可参考其 reward 实现而不是重造

**离线层（replay）**：采集真实 `uiautomator dump` XML、iOS 快照、网页 DOM
→ 存 `bench/fixtures/a11y/`；case = `{query, fixture, goldNode, goldAnswer}`。
任务族：聊天记录检索（给定微信/Telegram 树找某联系人某天的消息）、
内置 App 搜索（设置项/联系人/相册）、商品搜索（购物 App 树中比价）。

**指标**：gold 节点 hit@1、答案 EM/F1、SoM 树 token 预算（验证 <1.5KB 的声明）、
每查询耗 token 数。

**真机层（live）**：AndroidWorld 子集（先取 20 个检索型任务）在模拟器跑，
molasearch 作为 agent 的搜索工具，成功率用 AndroidWorld 的 reward 信号。

## 2. 场景二：30 模式真实管线 bench

**核心原则**：每个模式的题库必须匹配它的算法家族，且 **gold 判定四值**
（VERIFIED/REFUTED/UNVERIFIED/ABSTAIN）由人工标定，不由引擎自评。

**题库来源**：
- 中文深度搜索：[xbench-DeepSearch](https://xbench.org/agi/aisearch)（红杉中国，专为中文互联网搜索设计，已开源）
- 难检索事实：[BrowseComp-ZH](https://openai.com/index/browsecomp)（BrowseComp 中文版）、BrowseComp-Plus（固定语料版，可做纯检索对照）
- 时效题（M17/M19）：FreshQA（带时间戳 gold，专门测新鲜度）
- 多跳（M05/M06/M08/M09/M12）：MultiHop-RAG（2556 题，检索/生成分离评测）+ HotpotQA 子集
- 不可答 → ABSTAIN gold：SQuAD 2.0 式不可答子集 + 自建"零证据"题（引擎必须拒答，拒答率就是得分）
- 辟谣对（M13/M16）：自建 REFUTED/VERIFIED 配对题，gold 来自辟谣平台原文（人工标定）
- 代码（M23）：GitHub 真实 issue fixture；地理气象（M25）：存档天气 gold

**指标**：四值判定准确率、**ABSTAIN 精确率/召回率**（滥拒答与乱答都扣分）、
引用精确率（URL 可访问 + 域名权威级命中 gold）、support@k、
**延迟 vs 目录里 `latencyTargetMs` 的达标率**、每轮请求数（成本）、通道多样性。

**产出**：按模式的排行榜（markdown）+ JSONL 明细；
跨模式对照：M01 与 M05~M30 在同一题上的增益差，**直接暴露 §已知缺口里的
五个死开关**（死开关修复前后各跑一次，增益差就是修复证据）。

## 3. 场景三：策略热拔插 + RAG 选型矩阵 + 统一轨迹可视化

### 3a. 搜索策略 bench
同一题库 × 多种通道子集（全部 13 通道 / 仅 keyed / 仅 keyless / top3），
产出**质量-成本-延迟 Pareto 前沿**——这是"路由网关"提案（见目标架构）的数据依据。

**故障注入（hot-plug 的正确测法）**：在 `channelRunner` 注入层做 chaos——
bench 中途拔掉某通道（连败 / 超时 / 返回垃圾），断言：其余通道继续、
判定连续性（verdict 不因单通道死亡而翻转）、轨迹如实记录失败。
这与 magpie 路由哲学对齐："一个上游挂了，移到下一个候选"。

### 3b. RAG 后端矩阵
同一语料（≥500 条真实记录）+ 同一查询集，过全部 6 个 `Store` 后端：
recall@k、MRR、nDCG、p50/p95 延迟、写入吞吐、**跨后端排名一致性**
（同一查询各库 top-k 应在容差内一致）。方法论对齐
[BEIR](https://evidentlyai.com/blog/rag-benchmarks) 的检索评测协议；
多跳部分用 [MultiHop-RAG](https://github.com/yixuantt/MultiHop-RAG)。

### 3c. 层次循环（hop/snowball/gap 迭代）
断言循环必终止；逐轮记录**边际增益曲线**（每轮新增相关证据数——
RAAC 收敛判定的实证版）；stop 时机质量（早停 vs 跑满的得分差）。

### 3d. 统一轨迹可视化（通用逻辑的答案 = 一个 span schema + 每管线模板）
所有管线（调查、agent 注入、热迁移、盯梢差分、设备操控）发出**同一种 span**：

```
Span { traceID, parentID, name, start, dur, status,
       attrs: {modeID?, channel?, originAgent?, verdict?…} }
```

- 渲染器只有一套：瀑布图（span 时序）+ 依赖图（parent 树）+ 事件时间线；
- 每条管线只是一组 span 模板（调查 = origin→plan→channel*→rank→verdict；
  迁移 = backup→phase1→phase2→phase3；盯梢 = schedule→diff）;
- 与 OpenTelemetry 对齐（magpie 已有 `internal/otlp` 导出），外部 Jaeger
  和自家页面看同一份数据——**"每个 agent 和管线一套可视化"的通用解
  就是让它们说同一种 span**。

## 4. 场景四：视频搜索与拆帧（M27）

**借用基准**：
- [QVHighlights](https://proceedings.neurips.cc/paper/2021/file/62e0973455fd26eb03e91d5741a4a3bb-Paper.pdf)（时刻检索 + 高亮检测双任务，标准协议 R@k/IoU≥0.5 与 mAP）
- [MomentSeeker (2025)](https://arxiv.org/html/2502.12558v1)（长视频时刻检索，平均 >1200s，最贴近"B站长视频找名场面"）
- [MSR-VTT](https://www.microsoft.com/en-us/research/publication/msr-vtt-a-large-video-description-dataset-for-bridging-video-and-language)、[UVRB](https://www.modelscope.cn/datasets/iic/UVRB)（通用视频检索）

**molasearch 的做法**：取 5–10 个真实 B 站视频人工标注 gold 时刻区间 +
弹幕 XML 快照存 fixture；离线层回放 B 站 API，测：预测时刻 vs gold 的
R@k（IoU≥0.5）、弹幕密度峰值与 gold 的对齐率、**ffmpeg 3×3 关键帧的
token 成本实测**（验证 "-82%" 声明）、拆帧命中率对 VLM 预算的曲线。

## 5. 场景五：一切皆插件——一致性 conformance bench

magpie 的"插件与内置等价"靠 parity 测试守住；molasearch 对三个接口照搬：

| 接口 | conformance 套件内容 |
| --- | --- |
| `Store`（6 后端） | 同一套 upsert/all/search/close 用例 + 热迁移语义 + 备份可读 + SHA-256 不符拒绝切换 + 不可读时 fail-closed |
| `Embedder` | 维度、确定性（同文本同向量）、批量等价、余弦合理性、local 与 remote 在容差内的排序一致性 |
| `Channel`（13 通道） | Enabled/Keys 契约、解析 fixture 回放（真实页面存档）、超时、`errNoResults` 语义（零结果 ≠ 失败） |

**约定**：新后端/新通道/新嵌入模型 = 实现 + 通过 conformance 套件 = 可接入。
入口提案：`molasearch bench conformance --iface store --impl sqlite,vault,postgres,milvus,es,neo4j`。
矩阵报告即"多 kinder 后端/技能/嵌入模型自由选配"的兑现证据。
